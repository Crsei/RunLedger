# RunLedger Codex 提示词模板集

这些模板围绕“目标、范围、授权、完成证据”组织，适合在 RunLedger 中使用 Codex 开展开发工作。编写依据是本次对话对项目历史交流的抽查、当前 [AGENTS.md](../../AGENTS.md)，以及 [GPT-6 Astra 官方提示指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra)（2026-09-05 核对）。它们是项目使用建议，不是官方原文，也不声明历史缺陷仍然存在。

## 使用原则

替换 `【占位内容】`，删除没有实际信息的可选行。尽量写用户可观察的结果，把常规技术选择留给助手。小任务用一句话即可；跨模块任务再补充边界、验收和实施阶段。

根 AGENTS.md 已规定自主推进、并发改动保护、工程边界、验证和自动提交。模板仅补充本次任务信息；无需重复全部规则。只读任务不改文件、不提交；文档任务可以写指定文档；实现任务完成必要验证后按规则提交。推送需要明确授权。

本模板集不启用 API 功能、不修改模型参数，也不改变 RunLedger 产品内的多 Agent 或 sandbox 边界。

<a id="task-create"></a>
## 01 创建任务：先形成可执行计划

适合目标已知，但需要先确定范围、依赖与验收的工作。这里的“创建任务”指写实施计划文档，不默认创建外部工单。

```text
【需求】创建实施任务。
目标是为 RunLedger 的【用户可观察的结果】；本轮只做现状核实与计划文档。

先查开发索引、相关权威文档和生产代码，确认现状与缺口。
在【现有专题或目标路径】原地补充计划；确需新文档时更新所属入口。
计划包含：目标与非目标、相关模块、依赖顺序、可独立验收的阶段、
每阶段交付物和验证方式，以及需要用户决定的产品或兼容性问题。

常规技术方案给出推荐选择与理由；未证实的信息标为待核实。
本轮不修改生产代码，不把计划状态写成已实现。
文档检查通过后按 AGENTS.md 提交本任务文档。
```

<a id="task-execute"></a>
## 02 执行任务：按计划交付

```text
执行【计划文档路径】中的【阶段或任务编号】。
完成目标是【具体行为或交付物】；本轮范围截至【明确边界】。

先核对计划与当前代码、工作树是否一致，复用已经完成的部分。
沿计划依赖顺序实施，完成相关生产接线、必要测试和权威文档更新。
计划要求 RED→GREEN 时按该顺序推进。
常规实现选择自行决定；若计划与当前架构冲突，说明证据，
能在原目标内解决的继续处理，改变产品契约的部分再提问。

按 AGENTS.md 完成必要验证和本任务提交。
最终列出已完成项、验证证据、commit 和仍未关闭的验收项。
```

没有已有计划的小需求，可以直接用：

```text
实现【功能】，预期行为是【场景与结果】。
本次包含【范围】，完成相关接线、必要验证和文档更新后提交。
按 AGENTS.md 自主推进，常规实现选择自行决定。
```

<a id="debug-readonly"></a>
## 03 Debug：只读诊断

```text
只读排查 RunLedger 的【异常现象】。
复现操作：【步骤】；预期：【结果】；实际：【结果】。
可用线索：【发生时间、session ID、错误信息或日志位置；没有则删除】。

先确认实际可执行文件、进程、工作目录与会话数据来源，
再结合日志和相关生产代码定位失败环节。
需要复现时使用隔离环境，保留原始错误证据，不更改真实用户配置或数据。

给出：已确认原因、触发条件、影响、证据位置、最小修复方向。
区分事实和推测；证据不足时说明还缺什么。
本轮不修改文件、不提交。
```

<a id="debug-fix"></a>
## 04 Debug：复现并修复根因

```text
排查并修复【现象或上一条报告中的问题编号】。
预期结果：【正常行为与失败时的合理反馈】。
本轮只修复【范围】，其他发现记录后留待单独处理。

先复现或取得可验证的失败证据，再定位根因并修复。
缺陷修复尽可能加入能证明原问题的回归覆盖，验证相关生产入口。
保持权限治理和错误语义，不通过绕过检查、吞掉错误或扩大权限使测试通过。

按 AGENTS.md 完成必要检查；运行时代码构建后验证真实 CLI 对应路径。
更新相关故障或实施文档，验证通过后提交本任务改动。
最终说明修复前后行为、验证结果和仍有的实际限制。
```

<a id="refactor"></a>
## 05 重构代码：保持行为并改善结构

```text
重构【模块或文件】，解决【职责混杂、依赖环、重复逻辑等具体问题】。
本轮范围：【模块边界】；预期结构收益：【可检查的改进】。
公开接口、用户行为、持久化格式和权限语义保持一致。

先梳理调用方、依赖方向和现有行为测试，再实施最小必要拆分。
沿用现有抽象和版本约束，不为减少文件行数制造空壳或增加无用途层级。
验证关键调用路径与失败行为，必要时先补行为基线。
发现独立功能缺陷时记录；必须改变契约才能继续的部分先说明方案与影响。

按 AGENTS.md 完成验证、模块文档更新和本任务提交。
最终说明职责与依赖如何变化，以及行为保持的验证证据。
```

大范围拆包可先使用“创建任务”模板明确迁移阶段，再授权具体阶段。

<a id="documentation"></a>
## 06 构建文档：基于代码维护事实

```text
为【主题】编写或更新文档，面向【开发者、维护者或使用者】。
目标读者需要能完成【理解架构、配置功能、执行验证等具体目的】。
目标位置：【已有专题或用户指定目录】。

先读开发索引和已有相关文档，再核对当前代码、配置和生产接线。
优先更新现有权威文档；确需新建时更新所属 README 和总索引。
内容覆盖【需要的章节】，使用实际路径和具体流程解释关键关系。
明确区分当前实现、设计计划、自动化证据和待人工或外部环境验收项。
历史记录注明日期，不把旧测试数量或旧结论当作当前事实。

本轮仅修改文档。审阅差异、检查链接与规则一致性，运行 git diff --check。
无需代码测试或构建；完成后提交本任务文档。
```

如果只要聊天中的说明，把最后一段替换为：“本轮只在回复中说明，不写文件、不提交。”

<a id="cli-tui"></a>
## 07 CLI / TUI：验证用户能看到的行为

```text
实现或修复【CLI/TUI 场景】。
验收行为：
1. 在【操作】后显示或执行【结果】。
2. 在【窄终端、多行输入或其他边界场景】下仍可正常操作。
3. 取消、返回、失败和退出时表现为【预期结果】。

沿输入、命令、运行时与界面投影追踪完整路径，覆盖相关回归。
构建后核对实际 runledger 入口指向本仓库，使用隔离 RUNLEDGER_DIR 验证。
通过真实 TTY 或独立 tmux 会话检查上述行为与退出结果。
按 AGENTS.md 保留验证证据，只清理本任务产生的进程、会话和临时文件。

自动化、终端捕获、真实 provider 和人工视觉/键盘验收分别报告。
完成必要文档更新与本任务提交。
```

<a id="review"></a>
## 08 只读 Review：按影响报告发现

```text
只读审查【模块、提交范围或指定改动】，重点关注【风险或职责】。
审查范围以【路径或提交】为准；工作区其他改动只作为上下文。

核对实际生产调用链和相关测试，优先寻找可触发的行为缺陷、
权限或数据风险、生命周期问题及影响维护的结构问题。
每项发现包含严重程度、触发条件、后果、文件位置、证据与修复方向。
区分已复现和静态推断；不要为凑数量报告纯风格偏好。

不修改、不暂存、不提交。最终先给发现，再说明审查覆盖和未验证范围。
没有发现时直接说明，并列出仍有的验证局限。
```

<a id="comparison"></a>
## 09 跨仓库比较：提炼可采用方案

```text
只读比较 RunLedger 与【参考仓库】在【具体能力】上的实现。
先确认两边的分支、HEAD 和相关生产入口，注明比较基线。

按用户行为、职责边界、状态归属、错误处理和测试证据进行比较。
给出可以直接采用、需要适配和不适合采用的部分，以及理由。
建议必须符合 RunLedger 当前架构与工程边界；区分代码存在和生产接线完成。

本轮输出最小可执行建议，不改代码、不提交。
如要形成实施计划，另按文档任务范围落盘。
```

<a id="delegation"></a>
## 10 并行协作：作为主模板的补充

适用于可以独立核实的多个领域；开发子 Agent 的使用不改变产品内委派能力。

```text
请使用子 Agent 并行处理【可独立的子任务】。
每个子任务明确交付物、读取或修改的文件范围，并避免重叠写入。
主 Agent 同时推进其他独立工作，负责交叉核实、整合和最终验证。
共享入口的修改由主 Agent 统一处理。
只有能节省时间或提高质量的独立工作才委派，简单修改直接完成。
若当前环境不支持委派，说明限制后由主 Agent 继续。
```

<a id="continuation"></a>
## 11 续接任务和中途调整

继续同一任务：

```text
继续原任务，完成剩余的【实现、验证、文档或提交】。
沿用已确认的范围和决策，先核对当前工作树与已有结果。
复用仍有效的验证证据，不重复已完成且未受修改影响的检查。
若有阻碍，说明具体证据，同时完成仍能独立推进的部分。
```

补充验收：

```text
补充原任务的验收条件：【新场景及预期结果】。原任务继续。
```

旁支问题：

```text
旁支问题：【问题】。简短回答后继续原任务。
```

缩小范围：

```text
调整范围：本轮只完成【范围】，其余暂缓。
保留已经完成的改动，按新范围验证并报告剩余事项。
```

为新会话交接：

```text
整理当前任务的交接说明，输出到聊天中。
包括原目标、已授权范围、当前分支和任务改动、关键决策、
已执行验证及结果、未完成项与下一步。
区分本任务和并发改动，标出需要重新核对的运行时信息，不包含凭据。
本轮不继续实现、不新增文件或提交。
```

<a id="commit"></a>
## 12 整理提交：针对已有改动

适用于之前明确要求暂不提交，或需要补交的已有改动。常规实现任务已由 AGENTS.md 覆盖自动提交。

```text
审阅并提交【任务或明确路径】的已有改动。
先核对分支、身份、工作树和暂存区，确认本任务实际范围。
复用当前状态下仍有效的验证，补齐缺失的必要检查。
只暂存和提交本任务路径或 hunk，保护无关修改与已有暂存内容。
提交前审阅完整 staged diff，提交后核对 commit 和剩余状态。
本轮不推送。若验证或 hook 阻塞，按规则处理并如实说明。
```

<a id="short-prompts"></a>
## 适合保留的短提示词

日常小任务：

```text
请【修复或实现】【具体对象】，预期【可观察结果】。
按 AGENTS.md 完成本任务的必要验证和提交，简洁报告结果与剩余项。
```

避免无依据扩大范围：

```text
本轮范围以【问题或模块】为准。其他发现记录具体影响，不顺带扩展专项。
```

需要自主推进时：

```text
这是执行授权，请完成本次范围内的工作。
常规实现选择自行决定；只有答案会实质改变目标、兼容性或数据处理时才提问。
```

发现停顿来自指令时：

```text
如果某条 Skill 或项目指令阻止继续，请指出确切文件和条款，
区分明确要求与解释，并继续完成已经授权且不受阻的工作。
```

需要证据而非完成宣称时：

```text
请给出本次结论对应的实际证据，区分源码分析、测试、构建、
真实入口验证和人工验收。未执行的项目明确标出。
```

控制重复验证时：

```text
按 AGENTS.md 完成本次变更必需的验证。
同一状态下已经通过的检查复用结果；仅在新改动、失败或未解疑点影响结论时重跑。
```

控制最终回复长度时：

```text
最终用简洁中文说明结果、验证、commit 和实际阻碍。
优先给结论与必要证据，不复述完整执行过程。
```

## 常见措辞调整

| 容易产生歧义的表达 | 更具体的表达 |
|---|---|
| 创建任务 | 在指定专题写实施计划，本轮仅改文档 |
| 全面优化 | 改善指定模块的职责边界，写出可检查的结构目标 |
| 长期修复 | 修复指定问题根因，覆盖生产入口和回归测试 |
| 测试通过就算完成 | 按该变更所需的自动化、构建和实际入口验收完成 |
| 不要问任何问题 | 常规选择自行决定，实质改变目标或数据处理时才提问 |
| 全部提交 | 只提交明确任务范围，保护并发修改和已有暂存内容 |
| 继续 | 继续原任务的指定剩余交付，保留已有决策和有效证据 |

模板帮助表达目标，不保证工具权限、运行环境或外部依赖一定可用。发生实际阻碍时，应按证据报告并继续推进可完成部分。
